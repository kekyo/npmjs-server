# plan1 パッケージインポート機能

作成日: 2026-10-21

状態: 計画。機能の実装は未着手。

## 目的と採用方針

既存のプライベートnpmレジストリに公開したパッケージを、全バージョンと必要なメタデータを含めてnpmjs-serverへ移行する。最初の移行元はNexus 3とし、他のサーバーからも同じ取得・保存処理を利用できる構成にする。npmjs.org全体の複製は目的に含めない。

移行元には、直接公開されたパッケージだけを配信するレジストリURLを利用者が指定する。Nexus 3ではhostedリポジトリ、ArtifactoryではlocalリポジトリのURLが該当する。初版ではNexus 3のAPIによる自動列挙と、利用者が用意するパッケージ名一覧の入力を用意する。

キャッシュを除外する責任は移行元URLの選択条件として扱う。複数のリポジトリをまとめた入口の構成解析や、個々のパッケージの由来を推測する機能はインポート処理に持たせない。これにより、製品固有の処理を対象の列挙に限定する。

## 用語と移行元の条件

| 用語 | この計画での意味 |
| --- | --- |
| hosted / local | パッケージを直接公開・保管するリポジトリ。Nexus 3ではhosted、Artifactoryではlocalと呼ぶ |
| proxy / remote | 上流レジストリのパッケージを取得し、キャッシュするリポジトリ |
| group / virtual | 複数のリポジトリを一つのURLで配信する入口 |
| packument | パッケージ名を指定して取得するJSONメタデータ。バージョン一覧やタグなどを含む |
| tarball | npmパッケージの本体である`.tgz`ファイル |
| dist-tags | `latest`や`next`などの名前を、特定のバージョンへ対応付けるタグ |
| dry-run | 移行先へ保存せず、取り込み対象と実行条件を確認する実行方式 |

移行元URLの検索結果、packumentのバージョン一覧、tarballの取得内容は、すべて直接公開分に限定されていなければならない。検索にキャッシュが出ないことや、上流への新しい通信を止めたことだけでは、この条件を満たしたとは扱わない。

hostedへ手動でコピー・公開した外部パッケージは対象に含める。直接保管・公開しているパッケージを移すという目的に合致するためである。

初版では、利用者がこの条件を満たすURLを指定することを前提にする。URLの名前だけではリポジトリ種別を判定できないため、名前からhostedかどうかを推測しない。リポジトリ一覧の取得や種別の自動検証は必須機能にしない。

## 調査で確認した既存実装

### nuget-serverのインポート

参照したコードは`~/Projects/nuget-server/src/importPackages.ts`と`src/services/importService.ts`である。`--import-packages`で通常のHTTPサーバー起動から分岐し、接続先と認証情報を対話入力して、ローカルストレージへ保存する。

列挙にはNuGet V3の検索APIを使用し、空検索をページングした後、パッケージごとの全バージョンを取得している。hostedとproxyの区別はない。既存バージョンは上書きし、転送の一部が失敗してもCLIは終了コード0になり得る。また、バージョン一覧の取得失敗は警告として扱われ、最終的な転送失敗件数には含まれない。

npmjs-serverではCLIと処理本体の分離、対象の列挙と転送の分離、進捗表示を参考にする。NuGet固有の検索方法、取得URLの構成、アーカイブ形式は流用しない。無条件の上書きや失敗集計の扱いも引き継がない。

### npmjs-serverの保存と取得

| 現在のコード | 再利用できる内容と検討箇所 |
| --- | --- |
| [npmPublishService.ts](../../../src/services/npmPublishService.ts) | tarballの解析、名前の検証、ハッシュ計算、保存用データの生成。現在のpublish処理は公開日時を実行時刻にするため、そのままでは移行元の日時を保持できない |
| [npmProxyService.ts](../../../src/services/npmProxyService.ts) | tarballの取得、名前・バージョンの照合、チェックサム検証、上流のメタデータと公開日時の反映。インポートに必要な部分を共通化する候補 |
| [metadataService.ts](../../../src/services/metadataService.ts) | バージョン情報とdist-tagsの保存。既定のタグや未保存バージョンを指すタグの処理を、インポートに適用してよいか確認する |
| [server.ts](../../../src/server.ts) | 起動時に通常パッケージとプロキシキャッシュを別々に読み込む。インポート先は通常の`packageDir`とする |
| [npmルート](../../../src/routes/npm/index.ts) | 空検索でローカルのパッケージ名をページングできる。一方、プロキシ有効時のpackumentとtarballの取得は上流・キャッシュも対象になる |

現在のnpmjs-serverでも、ローカルの名前だけを検索した後に全バージョンを取得すると、同名の上流バージョンが含まれ得る。これが、移行元の条件を検索結果だけでなく取得内容にも適用する理由である。

## 対象の列挙

### Nexus 3

利用者は対象hostedリポジトリのnpm URLを直接指定する。例えば、`npm-internal`というhostedを作成している場合は次の形になる。実際のリポジトリ名と公開パスに合わせる。

```text
https://nexus.example.com/repository/npm-internal/
```

Nexus 3にはhosted、proxy、groupがあり、それぞれにリポジトリURLがある。hostedの直接指定によって、groupのメンバー解析とproxyキャッシュの除外処理を省ける。[Nexusのnpmリポジトリ](https://help.sonatype.com/en/npm-registry.html)、[リポジトリ種別](https://help.sonatype.com/en/repository-types.html)

全件列挙には指定したリポジトリに対する次のAPIを使用する。

```text
GET /service/rest/v1/components?repository=<repositoryName>
```

`continuationToken`を最後までたどり、パッケージ名を重複排除する。スコープ付きパッケージと複数バージョンを扱い、取得した項目が指定リポジトリのnpmパッケージであることを確認する。固定のページ件数には依存しない。[Components API](https://help.sonatype.com/en/components-api.html)

列挙後のpackumentとtarballは、指定したhostedのnpm APIから取得する。Components APIの結果だけではdist-tagsなどの移行に必要なメタデータがそろわないため、npmのメタデータ取得を共通処理にする。

NexusのREST APIとnpmレジストリの公開パスが異なる構成も考慮し、REST APIのベースURLとリポジトリ名を明示できる入力にする。具体的なCLIオプション名や入力形式は、実装時に既存の対話入力へ合わせて決める。

groupを利用できる権限だけでは、構成メンバーのリポジトリへ直接アクセスできるとは限らない。移行用の資格情報には、対象hostedと列挙APIを読み取る権限が必要になる。[リポジトリ種別とアクセス権](https://help.sonatype.com/en/repository-types.html)

### パッケージ名一覧

Nexus以外のサーバー、またはNexusの列挙APIを利用できない環境では、利用者が用意するパッケージ名一覧を入力する。各名前のpackumentから全バージョンを取得するので、利用者がバージョンを一つずつ列挙する必要はない。

この方式では一覧に指定したパッケージの移行を検証する。一覧にないパッケージまで含めて、移行元全体を網羅したとは扱わない。入力ファイルの形式は実装時に決め、スコープ付きの名前をそのまま記述できる形にする。

npmの`/-/v1/search`には検索とページングがあるが、任意の製品で空検索による全件列挙ができることまでは前提にしない。初版の共通処理に汎用検索による自動列挙は含めない。[npm Registry API](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md)

## 共通のインポート処理

### 実行形態と保存先

nuget-serverと同様に、`--import-packages`で起動するCLIを用意する。通常のHTTPサーバーは起動せず、接続先、列挙方式、認証情報、保存先を対話入力する。既存の設定・保存先の解決規則を利用する。

移行先のnpmjs-serverを停止した状態で実行し、通常の`packageDir`へ保存する。`proxy.packageDir`へ保存しない。別プロセスで追加したファイルを稼働中のサーバーへ自動反映する機能は、この計画に含めない。

dry-runでは移行先へ書き込まずにパッケージ名、バージョン、対象件数、列挙時の失敗を確認できるようにする。実行後は成功、同一内容のスキップ、競合、失敗を区別して報告する。

### 取得と保存する情報

tarballは再圧縮せず、取得したバイト列を保存する。内部の名前とバージョンが取り込み対象と一致することを確認し、移行元が提供するチェックサムと照合する。移行先で返すtarballのURLはnpmjs-serverのURLへ置き換える。

packumentは必要な情報を含む形式で取得し、各バージョンの公開日時、README、依存関係、`deprecated`などのメタデータとdist-tagsを保持する。移行元が提供しない情報は区別して報告し、元の値を復元できたとは扱わない。[npmのメタデータ仕様](https://github.com/npm/registry/blob/main/docs/responses/package-metadata.md)

通常のpublish処理を繰り返すだけでは、公開日時が実行時刻になり、追加順によって`latest`が変わり得る。インポートではパッケージの対象バージョンを取り込んだ後に、移行元のタグを反映する。取得できなかったバージョンを指すタグを、別のバージョンへ自動的に付け替えない。

検証が終わる前のファイルを完成済みパッケージとして扱わない。一時保存と公開済みデータの更新を分け、失敗や中断後も再実行できる保存手順にする。既存のパッケージやタグを破損させないことをテストする。

依存関係に記載された他のパッケージを再帰的に取得しない。外部の公開依存パッケージは移行後も通常のnpm設定や既存のプロキシ機能で取得する。

### 重複と再実行

同じ名前・バージョンが移行先に存在する場合は、tarballの内容が同一なら、その取得・保存を省略する。tarballの内容が違えば競合として報告し、自動で上書きしない。メタデータとタグの反映状態は別途確認し、tarballが同一であることだけを理由に反映を省略しない。既存の通常公開に対する重複ポリシーとは、インポートの既定動作を区別する。

複数のhostedを移す場合は、リポジトリごとに実行する。同じ名前・バージョンの競合を、リポジトリの暗黙の優先順位で解決しない。異なるリポジトリのタグが競合する場合の扱いも、既存タグを不用意に上書きしない方針で実装時に確定する。

再実行では対象を再列挙し、保存済みの内容を照合して、完了しているtarballの再取得を可能な範囲で省く。初版では専用の再開データベースや継続的な同期機能を設けず、保存済みデータと比較する方式を基本とする。tarballの保存後にタグの反映だけが未完了でも、再実行で完了できるようにする。

### 認証と失敗の扱い

移行元のBasic認証とBearer認証に対応する。認証情報は対象の接続先に限定して使用し、別の接続先へのリダイレクトで無条件に転送しない。対話入力やログ出力では秘密値を表示しない。

列挙失敗、メタデータ取得失敗、tarball取得失敗、内容の不一致、保存失敗、タグ反映失敗を最終結果に含める。処理できない項目を警告だけで対象から消さない。未完了または競合が残る場合は、終了コードを非ゼロにする。

個々のパッケージの失敗で他の処理を継続する場合も、完了した件数と失敗した件数を分ける。すべての処理を試みたことと、移行が成功したことを区別する。

## 初版の範囲外

以下はhosted URLを前提とする今回の方針では実装しない。

- group / virtualの構成解析、hostedリポジトリの自動探索・選択。
- proxyキャッシュの由来判定と、キャッシュが混在するURLからの自動選別。
- スコープ、tarballのホスト名、npmjs.orgでの同名パッケージの有無による由来の推測。
- Nexus以外の製品に対する専用列挙アダプターの一括実装。
- 管理UI、定期同期、依存関係の再帰取得、アカウント・権限の移行。
- 任意の検索APIを使った、移行元全体の網羅性が不明な自動インポート。

## 段階的な実装

各段階で、実行できるCLIと観測可能な結果を用意する。コード変更は振る舞いを検証するテストを先に追加し、REDを確認してから実装し、GREENを確認する。各段階を適切な粒度でコミットし、`feat:`、`fix:`、`refactor:`、`chore:`、`doc:`のヘッダを使用する。

計画から外れる問題が見つかった場合は、根本原因と計画の前提を見直してから変更する。不要になった修正やヘルパーは残さない。

### 段階1 パッケージ名一覧からのインポート

CLI、名前一覧の入力、共通のnpm取得・検証・保存処理を実装する。dry-run、移行元の認証、名前・バージョンとチェックサムの検証、必要なメタデータとタグの保存をこの段階で扱う。既存データと内容が異なる場合は上書きせずに報告する。

処理の分割にはinterfaceとファクトリ関数を使い、列挙方式を交換するための最小限の構成にする。必要な処理を既存のpublish・proxy実装から共通化する場合は、通常の公開・プロキシの振る舞いを維持する。

完了条件は次のとおり。

- スコープ付き・スコープなしのパッケージを、安定版とプレリリースを含めて取り込める。
- dry-runで対象を確認でき、移行先のパッケージとタグを変更しない。
- 移行先を起動し、実際の`npm view`と`npm install`で取り込んだパッケージを利用できる。
- tarballの内容、各バージョンの公開日時、提供されたメタデータとタグを検証できる。
- `latest`が最大バージョン以外を指す場合も、移行元の指定を保持する。
- 名前・バージョン・チェックサムの不一致と認証失敗を検出できる。
- 対応するテストとビルドが成功する。

### 段階2 Nexus 3の自動列挙

指定したhostedに対するComponents APIの列挙処理を追加し、段階1の共通処理につなぐ。REST APIのベースURLとリポジトリ名を指定できるようにし、複数ページ、スコープ付きパッケージ、名前の重複を扱う。

完了条件は次のとおり。

- ページングの最終ページまで列挙し、すべての対象パッケージを共通処理へ渡せる。
- 指定したhostedだけを参照し、groupやproxyのメタデータ・tarballを取得しない。
- hostedとproxyに同名パッケージが存在しても、hostedのバージョンだけを取り込む。
- 列挙APIが失敗した場合に、途中までの一覧を完全な一覧として成功報告しない。
- リバースプロキシの公開パスやAPIのベースURLが異なる構成をテストできる。
- Nexusの列挙APIを使えない場合も、名前一覧方式で段階1の機能を利用できる。
- 対応するテストとビルドが成功する。

### 段階3 再実行と移行結果の検証

同一内容のスキップ、競合の報告、中断後の再実行、タグ反映の再試行、失敗集計と終了コードを整える。既存の正常なパッケージを維持したまま、未完了の移行をやり直せることを確認する。

READMEなどの利用者向け説明には、移行元URLの条件、列挙方式、認証、移行先の停止、実行結果の読み方を記載する。日本語を原本として、必要な他言語の説明を更新する。この計画書へのリンクは一般ドキュメントに追加しない。

完了条件は次のとおり。

- 途中で転送や保存が失敗しても、再実行によって完了できる。
- 同じ内容を再実行しても重複せず、名前・バージョンが同じで内容が違うものは競合になる。
- タグを指すバージョンの取得失敗で、タグが別のバージョンへ変わらない。
- 完了済みパッケージだけが存在する場合も、未反映のタグを再実行で反映できる。
- 列挙からタグ反映までの失敗が最終結果に入り、未完了を終了コードで判定できる。
- 対象バージョン、tarballのハッシュ、保持対象のメタデータとタグを移行元と照合できる。
- 利用可能なNexus 3の実環境で、hostedからの移行と移行後のnpmクライアント利用を確認する。
- `npm test`によるビルドを含む全体テストが成功し、発生したウォーニングへの対処を終える。

## 全体の完了条件と実環境での確認

実装の完了時には各段階の完了条件に加えて、直接公開分だけを取り込むという移行元の条件が満たされていることを確認する。名前一覧方式の照合範囲は入力一覧、Nexus方式の照合範囲は指定hostedの全件とする。

実環境の検証前に、Nexus 3のバージョン、対象hosted、公開URL、REST APIの公開パス、利用可能な認証方式と読み取り権限を確認する。既存のメタデータやタグが欠ける場合の扱い、既存の移行先タグと競合した場合の扱いは、実装時に振る舞いとテストをそろえて確定する。

移行元を更新し続けると、列挙時と取得時の状態が変わる。最終的な移行結果の照合と切り替えは、移行元への公開とタグ変更を停止した状態で行う。利用可能な実環境がない場合は、実環境での確認を未完了として残し、自動テストの成功と区別する。
